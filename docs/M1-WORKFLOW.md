# M1 实施流程规划

> 配套文档：`docs/PLAN.md`（v0.2）
> 范围：M1 — 离线/微软登录、选择游戏目录、启动本地已安装版本
> 原则：每个阶段都必须“可构建、可验证、可回退”，避免一次性堆完再调试

---

## 1. 范围回顾

M1 完成后的能力：

1. 选择 `.minecraft` 目录并持久化
2. 离线登录、微软正版登录
3. 扫描本地版本并选择
4. 构建 classpath / 参数，启动本地文件完整的版本
5. 启动前完整性检查，缺失时列出清单
6. 日志可查看、可落盘

**不做**：下载、Java 自动安装、加载器安装、模组管理、版本隔离。

---

## 2. 阶段总览

| 阶段 | 内容 | 主要产出 | 复杂度 | 参考工作量 |
|------|------|----------|--------|-----------|
| P0 | 工程骨架与基础设施 | 依赖、目录、配置/日志/异常 | 低 | 0.5 人日 |
| P1 | 设置、游戏目录、Java 检测 | 设置持久化、Java 列表与匹配 | 低 | 1 人日 |
| P2 | 离线账号与账号管理 | 离线登录、账号增删切换 | 低 | 0.5–1 人日 |
| P3 | 版本扫描与继承解析 | 版本列表、合并后的版本模型 | 中 | 1.5–2 人日 |
| P4 | 启动构建与完整性检查 | classpath、natives、参数、缺失清单 | 高 | 2–3 人日 |
| P5 | 启动执行与日志 | 真实启动游戏、日志回传 | 中 | 1 人日 |
| P6 | 微软正版登录 | 系统浏览器 + 回环登录、令牌链、刷新（WebView2 兜底） | 高 | 1.5–2 人日 |
| P7 | 界面整合与打磨 | 主界面、错误提示、验收 | 中 | 1–1.5 人日 |

> 工作量仅用于判断优先级与拆分，不代表严格排期。

## 3. 阶段依赖关系

```text
P0 工程骨架
 │
 ├─► P1 设置/目录/Java ──────────────┐
 │                                   │
 ├─► P2 离线账号 ─────────────────┐  │
 │                                │  │
 └─► P3 版本扫描/继承解析 ──┐    │  │
                            │    │  │
                            ▼    ▼  ▼
                         P4 启动构建（依赖 P1/P2/P3）
                            │
                            ▼
                         P5 启动执行（离线端到端 ✅）
                            │
                            ▼
                         P6 微软登录（可独立并行开发，但联调在 P5 之后）
                            │
                            ▼
                         P7 整合打磨 → M1 验收
```

关键点：

- **P5 是第一个端到端里程碑**：离线账号 + 本地完整版本成功进入游戏。
- **P6 可以提前开发**（不依赖 P4/P5），但联调建议放在 P5 之后，避免同时排查“登录问题”和“启动问题”。
- P4 是风险最高的阶段，建议预留最多时间。

- [x] 主窗口最小壳（标题、日志面板占位）

**风险/注意**

### P3 — 版本扫描与继承解析

**目标**：读取本地版本，正确合并继承关系，供 UI 展示与启动使用。

**前置**：P1（需要游戏目录）。

**任务**

- [ ] `VersionJson` / `Library` / `Rule` / `Arguments` 等 JSON 模型
- [ ] `VersionScanner`：扫描 `versions/*/*.json`
- [ ] 容错：单个 JSON 损坏不影响其他版本
- [ ] `VersionResolver`：
  - [ ] 递归解析 `inheritsFrom`，检测循环
  - [ ] 子版本优先字段
  - [ ] `libraries` 合并与去重
  - [ ] `arguments` 合并（父在前、子在后）
  - [ ] `minecraftArguments` 兼容
- [ ] `RuleEvaluator`（可独立单测）
- [ ] 加载器类型识别（原版 / Forge / Fabric / NeoForge / Quilt）
- [ ] 版本列表 UI（名称、类型、时间）

**产出**：版本列表正确显示，选中版本可得到合并后的 `ResolvedVersion`。

**验证**

- 原版版本解析正确
- 有 `inheritsFrom` 的版本（Forge/Fabric）合并结果符合预期
- 父版本缺失时给出明确错误
- 循环继承不会死循环
- 损坏 JSON 被跳过并记录日志

**完成标志**

- 至少 1 个原版 + 1 个加载器版本解析通过
- 合并结果中的 `mainClass`、`libraries`、`arguments` 可人工核对
- 规则求值有单元测试

**风险/注意**

- 不同加载器 JSON 差异大：以官方继承规则为准，先覆盖常见情况
- 版本 id 与文件名不一致的情况：以 JSON 内 `id` 为准，但路径以目录为准
- 需要在测试前准备真实的版本 JSON（见 §5.3）

**目标**：把 `ResolvedVersion` 变成可执行的 Java 命令行，并在启动前发现缺失文件。

**前置**：P1、P2、P3。

**任务**

- [ ] `LibraryResolver`：
  - [ ] 规则过滤
  - [ ] Maven 路径推导（`downloads.artifact.path` 优先）
  - [ ] classpath 生成与去重
- [ ] `NativeExtractor`：
  - [ ] 旧版本（`natives` 字段）解压到 `<config>/natives/<versionId>`
  - [ ] 过滤 `META-INF`、`extract.exclude`
  - [ ] 新版本（独立 `natives-*` 库）走 classpath
- [ ] `ArgumentBuilder`：
  - [ ] 新/旧参数格式
  - [ ] 默认 JVM 参数
  - [ ] 变量替换（完整覆盖 PLAN §7.2）
  - [ ] 内存参数
- [ ] `LaunchValidator`：
  - [ ] client jar
  - [ ] libraries
  - [ ] assets index + objects
  - [ ] 汇总缺失清单（路径 + 分类）
- [ ] 调试输出：完整命令行（含脱敏 token）写入日志

**产出**：给定版本与账号，能生成完整 Java 命令行和缺失清单。

**验证**

- 完整版本：缺失清单为空，命令行结构正确
- 人为删除某个 library / assets 文件：能准确列出缺失项
- 旧版本（≤1.12）与 1.13+ 参数都能生成
- 旧版本 natives 能解压，目录内容正确
- 命令行中 token 不落明文日志（脱敏）

**完成标志**

- 命令行的 classpath、主类、参数人工核对无误
- 缺失清单可直接作为 M2 下载器的输入
- 不实际启动进程也能自测

**风险/注意**

- 这是最复杂阶段，建议先支持原版，再验证 Forge/Fabric
- natives 两代差异必须区分，否则 1.19+ 或旧版会失败
- 路径含空格/中文：全部用 `ArgumentList`，不要手工拼字符串
- assets objects 全量校验可能较慢：先校验索引 + 抽样，后续优化

## 5. 测试策略

### 5.1 单元测试候选（纯逻辑，优先覆盖）

| 模块 | 测试点 |
|------|--------|
| 离线 UUID | 稳定性、格式、大小写 |
| `RuleEvaluator` | 无规则、allow/disallow、os/arch、最后匹配 |
| `VersionResolver` | 继承字段覆盖、libraries 去重与顺序、循环继承 |
| `ArgumentBuilder` | 新旧格式、变量替换、含空格参数 |
| `LibraryResolver` | Maven 路径推导、classifier、规则过滤 |
| `LaunchValidator` | 缺失识别与分类 |
| Java 版本比较 | `1.8` vs `8`、`17` vs `21` |

> M1 允许先以“可执行 + 日志核对”为主，但上述解析类逻辑建议至少补关键单测，避免后续下载/安装功能返工。

### 5.2 手工集成测试

- 离线 + 原版（完整文件）
- 离线 + Forge/Fabric（有 `inheritsFrom`）
- 微软 + 原版
- 缺文件场景
- Java 不匹配场景
- 登录取消/网络错误场景

### 5.3 测试数据准备（重要）

当前 `%APPDATA%\.minecraft` 只有 `runtime`，**缺少 `versions` / `assets` / `libraries`**，因此：

1. 优先使用你现有其他启动器的游戏目录作为“游戏目录”进行联调（启动器支持任意目录）。
2. 若其目录结构完整，可直接作为 P3–P5 的测试数据。
3. 若需要独立测试数据，可在 P3 前准备一个最小原版版本目录（后续 M2 的下载器也可复用该结构）。
4. 测试时不要把启动器自身的配置写进该目录，避免污染。

## 8. 风险与回退

| 阶段 | 风险 | 回退/应对 |
|------|------|-----------|
| P0 | WebView2 包 restore 失败 | 先不引入包，P6 前再处理；或切换 NuGet 源 |
| P1 | Java 扫描慢/漏检 | 先支持手动指定，自动扫描作为增强 |
| P3 | 加载器 JSON 差异导致解析失败 | 先只支持原版，加载器作为增量；保留原始 JSON 便于排查 |
| P4 | natives/参数差异导致启动失败 | 用现有启动器的命令行对照；先原版后加载器 |
| P5 | 进程/编码问题 | 先同步等待并落盘日志，再优化实时回传 |
| P6 | Azure 应用配置/回环回调异常 | 集中配置 client_id 与回环端口；失败时回退 WebView2 |
| 全局 | 无测试数据 | 使用现有启动器目录；M2 下载完成后再做完整回归 |
